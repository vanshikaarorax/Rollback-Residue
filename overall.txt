Project: OPTIMIZER AUTOPSY
Core concept

Recover a hidden training trajectory from a final ML checkpoint by analyzing the optimizer state rather than the model weights.

Conceptually:

                    HIDDEN TRAINING PROCESS
                            │
             ┌──────────────┴──────────────┐
             │                             │
        model updates                 optimizer updates
             │                             │
             ▼                             ▼
       final weights                 m_t / v_t / step
             │                             │
             │                         SECRET SIGNAL
             │                             │
             └──────────────┬──────────────┘
                            ▼
                     checkpoint.pt
                            │
                     ┌──────┴──────┐
                     │   SOLVER    │
                     └──────┬──────┘
                            │
                   inspect optimizer
                            │
                   reconstruct events
                            │
                     decode bits
                            │
                         FLAG

PHASE 1 — Define the actual secret mechanism

This is the most important phase.

We need to decide exactly what information gets encoded.

I recommend:

hidden events
     ↓
gradient perturbations
     ↓
Adam update
     ↓
optimizer state
     ↓
checkpoint

For example:

A = gradient pulse on layer 1
B = gradient pulse on layer 2
C = sign inversion
D = gradient scaling

A hidden sequence:

A C B B D A C

becomes:

010011001...

and ultimately:

flag{...}

Keep the model extremely small.

Something like:

Input

  ↓

easier to explain in walkthrough

Then we can decide whether CNN makes the challenge more interesting.

PHASE 3 — Establish normal Adam training

Implement:

model = ...
optimizer = torch.optim.Adam(
    model.parameters(),
    lr=...
)

Train normally.

Save:

checkpoint = {
    "model": model.state_dict(),
    "optimizer": optimizer.state_dict(),
    "step": step,
}

Then inspect:

optimizer.state_dict()

You should see things equivalent to:

state
 ├── step
 ├── exp_avg
 └── exp_avg_sq

This is our baseline.

PHASE 4 — Understand the mathematics experimentally

Before encoding anything, create experiments around:

$$ m_t=\beta_1m_{t-1}+(1-\beta_1)g_t $$

and

$$ v_t=\beta_2v_{t-1}+(1-\beta_2)g_t^2 $$

We need to determine:

how much historical information survives
how many steps it survives
whether gradient signs are recoverable
how much numerical noise exists
whether m_t or v_t is more useful
whether model weights accidentally reveal the same signal

This should be a separate notebook:

research/
    optimizer_math.ipynb
PHASE 5 — Build the first encoder

Create something like:

encode_message(
    model,
    optimizer,
    message
)

Start ridiculously simple.

For example:

0 → positive gradient pulse
1 → negative gradient pulse

Run:

000000
000001
000010
...
111111

and see whether the final optimizer state distinguishes them.

PHASE 6 — Build the decoder

Then create:

decode_optimizer_state(checkpoint)

It should recover:

010011010...

from only:

optimizer.state_dict()

This is the first major proof-of-concept.

Do not continue until this works reliably.

PHASE 7 — Make the model weights a decoy

This is critical.

If:

model.state_dict()

directly exposes the secret, the challenge is bad.

We want:

model weights
     ↓
looks normal
     ↓
doesn't reveal message

while:

optimizer state
     ↓
contains recoverable historical signal

Test this explicitly.

Try:

weights-only analysis
optimizer-only analysis
weights + optimizer analysis

and document the difference.

PHASE 8 — Make the encoding less obvious

The naïve implementation might be:

positive = 0
negative = 1

That's too easy.

Instead, introduce a sequence of training events.

For example:

A = pulse layer 1
B = pulse layer 2
C = pulse layer 3
D = scale gradient

Then:

A B D C B A

represents the encoded message.

The solver first has to discover:

optimizer state contains evidence of different training events.

Only then can they decode the sequence.

PHASE 9 — Introduce ambiguity

This is where the challenge becomes a real CTF.

We should have:

checkpoint.pt

containing legitimate training history.

The hidden signal should be subtle.

For example:

normal optimizer state
+
small historical perturbations

rather than:

massive obvious tensor pattern

We need to avoid:

torch.mean(exp_avg)

immediately producing:

010101...
PHASE 10 — Create multiple candidate histories

This is where I think the challenge becomes genuinely good.

Create several possible training events:

History A
History B
History C
History D

They should produce similar model weights.

For example:

History A:
A → C → B → D

History B:
B → A → D → C

History C:
C → D → A → B

History D:
D → B → C → A

The final checkpoint corresponds to one.

The solver must determine which one.
